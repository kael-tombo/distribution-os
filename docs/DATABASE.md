# Distribution OS — Database Schema Reference

> Runtime-status note: [CURRENT_STATE.md](CURRENT_STATE.md) is authoritative
> for which schema capabilities are exercised by the golden path.

> Canonical column-by-column reference for every D1 table in
> Distribution OS. Includes indexes, foreign-key relationships, and
> the migration guide.

The schema is defined in [`db/schema.ts`](../db/schema.ts) using
Drizzle ORM's SQLite dialect. Migrations are generated by Drizzle Kit
into [`drizzle/*.sql`](../drizzle) and tracked by
[`drizzle/meta/_journal.json`](../drizzle/meta/_journal.json). There
are **23 physical tables** grouped into 16 logical domains (see
[`ARCHITECTURE.md`](./ARCHITECTURE.md#data-model) for the group
diagram).

## Conventions

| Convention             | Value                                                |
| ---------------------- | ---------------------------------------------------- |
| Primary keys           | `text` UUIDs (`crypto.randomUUID()`) for most tables; `integer AUTOINCREMENT` for `mission_events` and `audit_events`. |
| Timestamps             | `integer` epoch milliseconds (UTC).                  |
| Money                  | `integer` cents (e.g. `1999` → $19.99).              |
| Booleans               | `integer` 0/1 (Drizzle `mode: "boolean"`).           |
| JSON columns           | `text` containing JSON strings. Defaults: `"[]"` for arrays, `"{}"` for objects. |
| Workspace scoping      | Every tenant-scoped table has `workspace_id` as the first column after `id`, with `FOREIGN KEY … REFERENCES workspaces(id) ON DELETE CASCADE`. |
| Soft relationships     | Optional relations use `ON DELETE SET NULL` so deleting the parent doesn't lose the child record. |
| Indexes                | Every workspace-scoped query hits a composite index starting with `workspace_id`. |
| Enums                  | Declared as `as const` arrays in `db/schema.ts` (e.g. `ACTION_STATUSES`) and re-exported from the `*-pure.ts` modules. |

### `action_queue`

Approval-gated external actions. Each row is a single proposed outbound
operation (publish, outreach, spend, payment configuration) that must
be approved before execution.

| Column                   | Type      | Default     | Notes                                              |
| ------------------------ | --------- | ----------- | -------------------------------------------------- |
| `id`                     | text PK   |             | UUID.                                              |
| `workspace_id`           | text      |             | FK → `workspaces.id` (cascade).                    |
| `mission_id`             | text      |             | FK → `missions.id` (cascade).                      |
| `action_type`            | text      |             | e.g. `send_email`, `publish_post`, `configure_payment`. |
| `channel`                | text      |             | e.g. `email`, `linkedin`, `stripe`.                |
| `title`                  | text      |             | ≤200 chars.                                        |
| `summary`                | text      |             | ≤2000 chars.                                       |
| `payload_json`           | text      |             | Canonical-JSON payload (redacted in display).      |
| `payload_hash`           | text      |             | SHA-256 of canonical payload.                       |
| `risk`                   | text      | `medium`    | `low` / `medium` / `high`.                         |
| `status`                 | text      | `prepared`  | One of `ACTION_STATUSES`.                          |
| `blocker`                | text      | null        | Reason the action is blocked.                      |
| `decided_by`             | text      | null        | `userId` of approver/rejecter.                     |
| `decided_at`             | integer   | null        | Epoch ms.                                          |
| `expires_at`             | integer   |             | Epoch ms; defaults to +7 days.                     |

### `action_execution_attempts`

Durable Resend submission claims. Each row binds one action and immutable
payload hash to a database-unique provider idempotency key, tracks manual retry
count, and stores only the provider receipt or bounded error—not credentials.

Key columns are `workspace_id`, `mission_id`, `action_id`, `provider`,
`idempotency_key`, `payload_hash`, `status`, `attempt_count`,
`provider_request_id`, `receipt_json`, `error_code`, `error_message`, and the
start/completion timestamps.

**Indexes:** unique `(idempotency_key)`, `(workspace_id, action_id)`, and
`(status, updated_at)`.

```

missions    workspace_   workspace_   connector_     audit_events   organiza-    workspace_
            connections  settings     installations                  tions        (root)
   │                                   │

   ├── mission_versions                 │
   ├── strategy_versions                 │
   ├── evidence                          │
   ├── experiments ──────────┐          │
   ├── action_queue ─────┐   │          │
   │      │              │   │          │
   │      ├── content_assets ◀──────────┘
   │      ├── payments ◀───────── experiments
   │      └── touchpoints ◀──────── experiments
   ├── payments
   ├── touchpoints
   ├── contacts (mission_id SET NULL on delete)
   └── agent_runs
         │
         └── agent_steps

organizations
   ├── organization_memberships
   └── organization_invitations
```

### Notes

- Every tenant-scoped table (except `organizations` and its children)
  has `workspace_id` as a foreign key to `workspaces.id` with
  `ON DELETE CASCADE`.
- Optional relations (`action_id`, `experiment_id` on payments /
  touchpoints / content_assets) use `ON DELETE SET NULL` so deleting
  the parent doesn't lose the child record.
- `organizations.id` equals the `workspaces.id` — there is exactly one
  organization per workspace.
- `audit_events` is workspace-scoped via `ON DELETE CASCADE`, so the
  data-deletion endpoint writes its audit row BEFORE the cascade to
  preserve the deletion-intent record.

## Migration guide

### Generate a new migration

After editing `db/schema.ts`:

```bash
npm run db:generate
```

This runs `drizzle-kit generate` through the Sites runtime shim. A new
`drizzle/XXXX_<slug>.sql` file is created and the journal is updated.

### Apply migrations

| Environment | Command                                                                  |
| ----------- | ------------------------------------------------------------------------ |
| Local       | `npx wrangler d1 migrations apply DB --local`                            |

The local D1 instance is migrated automatically on first run of
`npm run dev`.

### Writing a manual migration

Drizzle Kit occasionally produces destructive operations (e.g. `DROP
TABLE` for a column rename). When that happens:

1. Delete the auto-generated file.
2. Write a manual `drizzle/XXXX_<slug>.sql` that preserves data (e.g.
   `ALTER TABLE … RENAME COLUMN …`).
3. Update `drizzle/meta/_journal.json` with the new entry.
4. Update `drizzle/meta/XXXX_snapshot.json` to reflect the new schema
   state (Drizzle Kit regenerates this if you re-run `db:generate`
   after reverting).

### Inspecting the schema

The live D1 schema can be inspected via:

```bash
npx wrangler d1 execute distribution-os-prod --remote \
  --command ".schema"
```

## Deletion cascade order

`POST /api/data-deletion` wipes the tenant tables in this exact FK-safe
order (children before parents):

```jsonc
[
  "agent_steps",
  "agent_runs",
  "mission_events",
  "mission_versions",
  "strategy_versions",
  "evidence",
  "payments",
  "touchpoints",
  "content_assets",
  "experiments",
  "action_queue",
  "contacts",
  "workspace_settings",
  "workspace_connections",
  "connector_installations",
  "missions"
]
```

The `workspaces` row is intentionally preserved so the user can still
sign in afterward — deletion wipes mission / connector / evidence state,
not the account. The `audit_events` row recording the deletion is
written BEFORE the cascade so it survives long enough to be replicated
/ exported by the compliance pipeline.

See [`SECURITY.md`](./SECURITY.md#gdpr-compliance) for the full GDPR
discussion.
