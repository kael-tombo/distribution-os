# Distribution OS — Deployment Guide

> Runtime-status note: verify release claims against
> [CURRENT_STATE.md](CURRENT_STATE.md) before deploying.

> End-to-end deployment reference for Distribution OS on Cloudflare
> Workers + D1. Covers local development, preview deploys, production
> deploys, database migrations, environment variables, and monitoring.

Distribution OS ships as a single Cloudflare Worker fronted by Next.js
16 (App Router) via `vinext`. The database is Cloudflare D1 (SQLite).
Migrations are generated by Drizzle Kit from `db/schema.ts`. Identity is
provided by the ChatGPT hosting control plane via request headers —
there is no own password store to deploy.

## Local development

The Sites runtime shim (`scripts/sites-env.sh`) sets up an isolated
HOME, npm cache, and wrangler registry under `.sites-runtime/` so builds
are reproducible and do not pollute the developer's `$HOME`.

### 1. Install dependencies

```bash
npm run install:ci
```

This runs `scripts/install-ci.sh`, which:

1. Validates the writable install environment (HOME, npm cache).
2. Acquires an exclusive `flock` to prevent overlapping installs.
3. Preflight-verifies the locked `vinext` tarball URL + integrity from
   `package-lock.json`.
4. Runs `npm ci --cache .sites-runtime/npm-cache` with bounded sockets
   and timeouts.
5. Verifies `node_modules/.bin/vinext` is executable.

### 2. Configure local environment

Copy `.env.example` to `.dev.vars` and fill in the secrets you want to
test against (leave them blank for simulation mode):

```bash
cp .env.example .dev.vars
$EDITOR .dev.vars
```

The dev server reads `.dev.vars` via the Cloudflare Vite plugin. The D1
binding is configured in `vite.config.ts` (read from
`.openai/hosting.json`).

### 3. Start the dev server

```bash
npm run dev
```

This launches Vite + vinext + the Cloudflare Vite plugin with local
D1 + R2 bindings. Open `http://localhost:5173`.

### 4. Identity headers

The dev server expects identity headers
(`oai-authenticated-user-id`, `oai-authenticated-user-email`) to be
injected by the hosting control plane. For local development without
those headers:

- Every authenticated route returns `401 AUTH_REQUIRED`.
- The landing page renders the "Sign in" CTA.
- `POST /api/mission` falls back to `mode: "simulation"` when
  `OPENAI_API_KEY` is unset.

To test authenticated routes locally, use `curl` with explicit headers:

```bash
curl http://localhost:5173/api/workspace \
  -H "oai-authenticated-user-id: user_test_001" \
  -H "oai-authenticated-user-email: ada@example.com"
```

## Cloudflare D1 database creation

Distribution OS expects a single D1 database bound as `DB`. Create it
once per environment:

### Production

```bash
npx wrangler d1 create distribution-os-prod
```

The command outputs a `database_id`. Copy it — you'll need it in the
next step.

### Preview / staging

```bash
npx wrangler d1 create distribution-os-preview
```

### Local

The Cloudflare Vite plugin provisions a local D1 instance under
`.wrangler/` automatically. No creation step is needed.

## Wrangler configuration

Distribution OS does not ship a `wrangler.toml` — bindings are declared
in `vite.config.ts` and read from `.openai/hosting.json` (which is
generated by the hosting control plane). To deploy with `wrangler`
directly, create a `wrangler.toml` at the repo root:

```toml
# wrangler.toml — production overrides
name = "distribution-os"
main = "./worker/index.ts"
compatibility_date = "2025-01-01"
compatibility_flags = ["nodejs_compat"]

[vars]
OPENAI_MODEL = "gpt-5.6"

[[d1_databases]]
binding = "DB"
database_name = "distribution-os-prod"
database_id = "<the id returned by wrangler d1 create>"

# Optional R2 bucket (not currently used):
# [[r2_buckets]]
# binding = "ASSETS"
# bucket_name = "distribution-os-assets"
```

Secrets (do NOT put these in `wrangler.toml`):

```bash
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put STRIPE_WEBHOOK_SECRET
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put RESEND_WEBHOOK_SECRET
```

For a preview environment, create a second `wrangler.preview.toml` with
a different `database_id` and `name = "distribution-os-preview"`.

## Environment variables

### Workers secrets (production)

| Secret                  | Required | Purpose                                                          |
| ----------------------- | -------- | ---------------------------------------------------------------- |
| `OPENAI_API_KEY`        | no       | When set, missions are generated with the live model. Otherwise simulation mode. |
| `STRIPE_WEBHOOK_SECRET` | no       | `whsec_...` for verifying Stripe webhook signatures. When unset, `POST /api/webhooks/[provider]` returns `503`. |
| `RESEND_API_KEY` | no | Sending-only credential for the narrow email adapter. |
| `RESEND_WEBHOOK_SECRET` | no | Verifies signed Resend delivery events from the raw request body. |
| `RESEND_WORKSPACE_ID` | no | Exact single workspace allowed to use the site-level Resend credential. |
| `RESEND_FROM_EMAIL` | no | Exact sender accepted at the execution boundary. |
| `RESEND_ALLOWED_RECIPIENTS` | no | Comma-separated sandbox allowlist; empty means no outbound email. |

### Workers vars (non-secret configuration)

| Var            | Default    | Purpose                                              |
| -------------- | ---------- | ---------------------------------------------------- |
| `OPENAI_MODEL` | `gpt-5.6`  | Override the Responses API model used by `POST /api/mission`. |

### Bindings

| Binding | Type   | Required | Purpose                                                |
| ------- | ------ | -------- | ------------------------------------------------------ |
| `DB`    | D1     | yes      | SQLite database for all workspace-scoped tables.       |
| `ASSETS`| R2     | no       | Optional bucket for large uploaded assets (future).    |

### Local development (`.dev.vars`)

The Cloudflare Vite plugin reads `.dev.vars` (gitignored) for local
secrets. Mirror the same names as production:

```bash
# .dev.vars
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-5.6
STRIPE_WEBHOOK_SECRET=whsec_...
```

### Reference

See [`.env.example`](../.env.example) for the canonical, up-to-date
list of variables. The `.env.example` file is the single source of
truth — update it whenever a new variable is introduced.

## Database migrations

Migrations are generated by Drizzle Kit from `db/schema.ts` and live in
`drizzle/*.sql`. The migration journal is `drizzle/meta/_journal.json`.

### Generate a new migration

After editing `db/schema.ts`:

```bash
npm run db:generate
```

This runs `drizzle-kit generate` through the Sites runtime shim. A new
`drizzle/XXXX_<slug>.sql` file is created and the journal is updated.
Commit the new file alongside the schema change.

### Apply migrations locally

Docker startup applies pending migrations automatically. Before using
`npm run dev` directly, apply migrations to the same local D1 state:

```bash
npm run db:migrate:local
```

### Apply migrations to preview

```bash
npx wrangler d1 migrations apply distribution-os-preview --remote
```

### Apply migrations to production

```bash
npx wrangler d1 migrations apply distribution-os-prod --remote
```

> Always apply migrations to preview first and smoke-test before
> promoting to production. D1 migrations are not transactional across
> statements — a partial failure leaves the database in an
> inconsistent state.

## Production deployment

### 1. Build the Worker

```bash
npm run build
```

This runs `scripts/build-verified.sh`, which invokes
`vinext build` under a bounded timeout (default 3 minutes, configurable
via `SITES_BUILD_TIMEOUT`). The build output is placed in `dist/`.

### 2. Apply migrations

```bash
npx wrangler d1 migrations apply distribution-os-prod --remote
```

### 3. Deploy the Worker

```bash
npx wrangler deploy
```

If you're using a `wrangler.toml` with a custom `name`, the deploy
creates / updates the named Worker. The first deploy of a new Worker
prints the production URL (`https://distribution-os.<account>.workers.dev`).

### 4. Configure the custom domain (optional)

```bash
npx wrangler domains attach distribution-os.example.com
```

Or via the Cloudflare dashboard: Workers & Pages → distribution-os →
Settings → Triggers → Custom Domains.

### 5. Verify

```bash
# Health check (anonymous — should return 200 landing page HTML)
curl -sS https://distribution-os.example.com/ | head -5

# Authenticated check
curl -sS https://distribution-os.example.com/api/workspace \
  -H "oai-authenticated-user-id: user_test_001" \
  -H "oai-authenticated-user-email: ops@example.com"
```

### 6. Smoke-test the mission flow

```bash
curl -sS -X POST https://distribution-os.example.com/api/mission \
  -H "oai-authenticated-user-id: user_test_001" \
  -H "oai-authenticated-user-email: ops@example.com" \
  -H "Content-Type: application/json" \
  -d '{"website_url":"https://example.com"}'
```

When `OPENAI_API_KEY` is set, the response should include
`"mode":"live"`. Otherwise `"mode":"simulation"`.

## Preview deploys

Every pull request should be deployed to a preview Worker + preview D1
database before merging. The recommended setup:

1. **One preview database per branch** (or one shared preview database
   if you're cost-conscious). Create via:

   ```bash
   npx wrangler d1 create "distribution-os-pr-$PR_NUMBER"
   ```

2. **Generate a per-PR `wrangler.preview.toml`** with the preview
   database id and `name = "distribution-os-pr-$PR_NUMBER"`.

3. **Apply migrations** to the preview database.

4. **Deploy** the preview Worker:

   ```bash
   npx wrangler deploy -c wrangler.preview.toml
   ```

5. **Post the preview URL** on the PR for reviewer access.

Preview Workers inherit the production secrets unless overridden — be
careful with `OPENAI_API_KEY` and `STRIPE_WEBHOOK_SECRET` in preview.
Recommended: use test-mode keys for preview.

## Monitoring

### Cloudflare dashboard

- **Workers & Pages → distribution-os → Metrics** — requests, CPU time,
  errors, durations.
- **Workers & Pages → distribution-os → Logs** — real-time tail (enable
  Logpush to a destination for retention).
- **D1 → distribution-os-prod → Metrics** — query count, rows read,
  rows written, storage size.

### Application-level observability

Distribution OS emits three signals:

1. **`audit_events` table** — queryable via `GET /api/audit?category=…`
   or directly in D1. Categories: `auth, role, approval, connector,
   action, payment, export, deletion, security, config`.
2. **`agent_runs` / `agent_steps` tables** — per-agent token, cost
   (cents), latency. Surfaced in the workspace `memory` view.
3. **`lib/observability-pure.ts`** — structured `Metric` and `LogEntry`
   builders with correlation id, mission id, workspace id. The Worker
   can ship these to a Tail Worker for fan-out to Logpush / external
   observability platforms.

### Recommended alerts

| Alert                                       | Threshold                | Action                          |
| ------------------------------------------- | ------------------------ | ------------------------------- |
| Worker error rate                           | > 1% over 5 min          | Page on-call.                   |
| Worker p95 latency                          | > 2 s over 5 min         | Investigate slow routes.        |
| D1 storage size                             | > 80% of plan limit      | Plan capacity increase.         |
| `monthly_spent_cents` approaching cap       | `severity = critical`    | Notify workspace owner.         |
| `audit_events` with `event_category=deletion` | any in production      | Notify compliance.              |
| Stripe webhook verification failures        | > 0 in 1 hour            | Investigate replay / forgery.   |
| Rate-limit denials per workspace            | > 100 in 5 min           | Possible runaway agent loop.    |

### Health check endpoint

There is no dedicated `/health` route today — the landing page
(`GET /`) serves the same purpose: a 200 response means the Worker is
up, the static assets are bound, and the App Router is rendering.

## Rollback

### Worker rollback

Cloudflare Workers supports instant rollback to the previous version
via the dashboard or CLI:

```bash
npx wrangler deployments list
npx wrangler deployments rollback --version-id <previous-version-id>
```

### D1 rollback

D1 does not support automatic rollback of migrations. To revert a
migration:

1. Write a **down migration** in `drizzle/` that reverses the schema
   change (e.g. `DROP TABLE`, `DROP COLUMN`).
2. Apply it via `wrangler d1 migrations apply --remote`.

> Data lost by a forward migration cannot be recovered unless you have
> a D1 backup. Schedule periodic D1 backups via the dashboard or
> `wrangler d1 backup create`.

### Emergency data-deletion

If a workspace's data must be wiped immediately (e.g. compliance
incident), use the data-deletion endpoint:

```bash
curl -X POST https://distribution-os.example.com/api/data-deletion \
  -H "oai-authenticated-user-id: user_to_wipe" \
  -H "oai-authenticated-user-email: wipe@example.com" \
  -H "Content-Type: application/json" \
  -d '{"confirm":"DELETE"}'
```

This wipes tenant tables in FK-safe order. The audit row is written only after
the deletion batch succeeds. See
[`SECURITY.md`](./SECURITY.md#gdpr-compliance) for details.

## Troubleshooting

### `vinext is unavailable. Run npm run install:ci`

The Sites runtime shim cannot find `node_modules/.bin/vinext`. Re-run
`npm run install:ci`. If it still fails, delete
`.sites-runtime/` and `node_modules/` and try again.

### `D1 binding missing` (HTTP 500 from any /api route)

The `DB` binding is not configured. Check `vite.config.ts` (for local
dev) or `wrangler.toml` (for production). Verify the binding name
matches what `db/index.ts` expects (`DB`).

### `401 AUTH_REQUIRED`

Identity headers are missing. For local dev, pass them explicitly with
`curl -H`. For production, verify the ChatGPT control plane is
configured to inject `oai-authenticated-user-id` and
`oai-authenticated-user-email`.

### `503 Stripe webhook secret is not configured`

`STRIPE_WEBHOOK_SECRET` is unset. Set it via
`npx wrangler secret put STRIPE_WEBHOOK_SECRET` (production) or in
`.dev.vars` (local).

### `mode: "simulation"` when you expected `live`

`OPENAI_API_KEY` is unset. Set it via
`npx wrangler secret put OPENAI_API_KEY` (production) or in `.dev.vars`
(local).

### Migration fails with `FOREIGN KEY constraint failed`

You're trying to delete or modify a parent row that still has child
rows. Use the FK-safe deletion order documented in
[`SECURITY.md`](./SECURITY.md#gdpr-compliance) and the
`data-deletion` route handler.

### Build hangs / times out

The verified build script caps vinext at 3 minutes
(`SITES_BUILD_TIMEOUT`). If your machine is slow, override the
timeout:

```bash
SITES_BUILD_TIMEOUT=10m npm run build
```

### `npm ci` overlaps with another install

The Sites runtime uses `flock` to refuse overlapping installs in the
same project root. Wait for the other install to finish, or remove
`.sites-runtime/install.lock` if it's stale (e.g. after a crash).
